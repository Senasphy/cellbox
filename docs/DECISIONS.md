# Decisions

## Phase 0

- Context: The specification requires prefixed sortable ULIDs, and the environment has no guaranteed network access for Go modules. Decision: Encode a 48-bit UTC millisecond timestamp and 80 bits from `crypto/rand` with the ULID Crockford alphabet using the standard library. Consequence: IDs remain sortable and ULID-shaped without another dependency; monotonic ordering for IDs generated in the same millisecond is not guaranteed.
- Context: Database writes need a single writer and zero setup. Decision: Use modernc SQLite with one open connection and WAL mode. Consequence: Pure Go builds work without CGO; write concurrency is serialized.
- Context: The first phase needs a runnable doctor before native runtime checks exist. Decision: Report baseline OS and cgroup-v2 presence and label delegation checks as not implemented. Consequence: Doctor is explicitly incomplete until Phase 4.
- Context: The Docker backend requires a configurable Engine or Podman-compatible Unix socket. Decision: Add `docker_socket` with `/var/run/docker.sock` as the default and a `CELLBOX_DOCKER_SOCKET` override. Consequence: The endpoint follows the rest of the config layering and remains optional for the native backend.

## Phase 1

- Context: The Docker Engine API has no endpoint to signal one `exec` process independently. Decision: On an exec timeout, stop the containing Docker container so the workload process tree cannot keep running, and treat kill requests against an already stopped or missing container as successful. Consequence: The whole session is marked failed after a timeout; this is a bootstrap-backend limitation and is less precise than the native process supervisor.
- Context: The public API specifies a signal endpoint, while the Docker Engine backend cannot signal an individual exec. Decision: Route signals through the active runtime exec handle and return `capability_unsupported` when that backend reports `ErrUnsupported`. Consequence: Backends with process-level signal support can provide the endpoint; Docker clients receive an explicit limitation instead of a misleading success.
- Context: Docker per-container storage quotas are not available with common storage configurations; for overlay2 Docker documents that they require an XFS backing filesystem mounted with project quotas ([Docker Engine daemon reference](https://docs.docker.com/reference/cli/dockerd/)). Decision: The Docker runtime does not claim or set a disk limit, advertises `disk_limits: false`, reports `disk_mb: 0` when no disk quota is requested, and rejects explicit disk limit requests. Consequence: Docker sessions have no enforced writable-layer size cap and remain unsuitable for hostile workloads; a future backend can advertise this capability only when enforcement is reliable.
- Context: Network allowlists and proxying are not implemented in the first backend slice. Decision: Accept only an empty policy or `{"mode":"none"}` and always create Docker containers with `NetworkMode=none`. Consequence: Any requested network access fails closed until the egress phase is implemented.
- Context: The API requires cursor pagination but does not specify page sizes or ordering. Decision: Use opaque URL-safe cursors over stable sort keys, default to 50 rows, and cap pages at 200; sessions sort newest first, execs oldest first, and directory entries by path. Consequence: List responses stay bounded and clients can continue without offset scans.

## Phase 2

- Context: The API key model requires per-key quotas but does not define provisioning defaults or a quota-management API. Decision: New session keys receive 20 active sessions, 8192 MB aggregate memory, and 20 requests per second; admin keys remain unmetered. Capacity pressure is rejected immediately with `capacity_exceeded` and `Retry-After`, using host or cgroup resource ceilings and configured overcommit ratios. Consequence: The service enforces bounded defaults without adding an undocumented key-management operation; configurable per-key quota editing and wait-queue admission remain future work.
- Context: The service needs a small Prometheus scrape endpoint during the reliability phase. Decision: Emit the current bounded metric set in the Prometheus text exposition format directly from the standard library. Consequence: The endpoint has no additional runtime dependency; automatic HTTP request metrics and some runtime-specific metrics remain unimplemented.
- Context: The specification describes one actor goroutine per session. Decision: Keep the single-node SQLite implementation serialized through transactions that validate each lifecycle transition instead of adding per-session goroutines in Phase 2. Consequence: Persisted state changes remain ordered, but there is no actor-local command queue or actor-specific scheduling; those can be added if runtime concurrency requires them.
