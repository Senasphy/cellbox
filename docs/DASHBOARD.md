# Dashboard authentication

The dashboard exchanges an API key for a browser session with `POST /v1/auth/session` and JSON `{"api_key":"cbx_…"}`. The key is verified through the API and kept only in server memory. The browser receives a 12 hour `cellbox_session` cookie marked `HttpOnly`, `SameSite=Strict`, and `Secure` whenever the request uses TLS. The response also includes a random CSRF token and sets a matching `cellbox_csrf` cookie. The UI keeps the CSRF value in tab memory and sends it as `X-CSRF-Token` for POST, PUT, PATCH, and DELETE requests.

`DELETE /v1/auth/session` invalidates the server-side session and expires both cookies. Session cookies stop working after a service restart; the user signs in again with the API key. API clients can continue to use bearer keys directly. The dashboard does not put keys in localStorage or sessionStorage.

The dashboard provides Overview and Sessions navigation, session create/destroy, streamed command output, and session detail views for Terminal, Timeline, Files, Metrics, and Events. Overview shows active sessions, CPU, memory, and PID capacity gauges, and create/error rate sparklines derived from successive Prometheus counter samples. The Files tab has a lazy paginated directory tree, drag-and-drop upload, tar download, and a dynamically loaded read-only CodeMirror 6 viewer. A keyboard command palette opens with Ctrl+K or ⌘K and supports navigation and common actions. A light/dark theme toggle, visible keyboard focus, and reduced-motion styles are present; a full WCAG AA audit remains pending. Session snapshots refresh over authenticated SSE with client-managed exponential reconnect backoff; the table supports filters, labels, age, and bulk destroy. The Metrics tab streams per-session CPU, memory, PID, and I/O samples into uPlot, with the configured CPU, memory, and PID limits drawn as lines. Admin keys can be listed, created, and revoked; a new secret is shown once. The System view shows runtime capabilities and Prometheus text metrics. Images lists images referenced by current sessions; the API does not yet expose image management.

Phase 3 still lacks doctor data and recent limit-breach events on the overview, CPU and memory sparklines in the session table, an xterm.js terminal, a virtualized timeline/output viewer, complete light/dark theme coverage, and an accessibility audit. The file viewer currently treats files as text and does not provide syntax-specific language modes. Warm pool status is currently shown as unavailable because neither runtime advertises that capability. Effective configuration is not exposed by the current API. Network, snapshot, and replay views depend on later phases.
